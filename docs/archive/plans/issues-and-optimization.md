# AquaSentinel 问题分析与优化路线图

## 1. 架构层面问题

### P1-01: 服务间通信缺乏消息中间件

**现状**：YOLO Service 通过 WebSocket 直连 Backend 推送 AI 检测结果。一旦 WebSocket 断开或 Backend 重启，报警事件丢失，无重试机制。

**影响**：
- 报警事件是溺水安全的核心数据，丢失意味着漏报
- WebSocket 重连期间的事件无法补偿
- 无法实现事件回溯和审计

**量化影响**：
- 当前 0 条消息持久化保障
- WebSocket 断连 → 0% 事件投递保证（无重试）
- 无法衡量断连期间丢失事件数（无监控）

**优化方案**：引入 RabbitMQ / Redis Streams
- YOLO Service → MQ → Backend 消费，保证至少一次投递
- 新增 `monitoring_event` 表的异步写入保障

**预期效果**：
| 指标 | 当前 | 优化后 |
|------|------|--------|
| 事件投递保证 | 0%（断连即丢） | ≥99.9%（MQ 持久化+重试） |
| 断连期间事件 | 全部丢失 | MQ 缓冲，重连后消费 |
| 可审计事件数 | 仅成功写入部分 | 100% 可追溯 |

---

### P1-02: YOLO Service 任务状态纯内存存储

**现状**：推理任务状态 `_TASKS: dict[str, EngineTaskState]` 存于 Python 进程内存，进程重启后所有任务丢失。

**影响**：
- 进程崩溃/重启后，所有推理任务停止，需人工逐一重启
- 无法从外部查询任务历史（如最近 24 小时启停记录）
- 多实例部署时任务状态不共享

**量化影响**：
- 进程重启后恢复时间：手动逐任务重启 ~5-10 分钟/摄像头
- 任务历史数据：0 条可追溯

**优化方案**：
- 任务启动/停止事件持久化到数据库（已有 `ai_stream_task` 表）
- 重启后自动恢复 `RUNNING` 状态的任务

**预期效果**：
| 指标 | 当前 | 优化后 |
|------|------|--------|
| 进程重启恢复 | 手动 5-10 分钟 | 自动 <30 秒 |
| 任务历史可追溯 | 0 | 100% |
| 多实例任务感知 | 不支持 | 支持 |

---

### P1-03: 无容器化部署方案

**现状**：四个服务缺少统一的容器化部署方案，手动部署依赖运维经验。

**影响**：
- 环境一致性无法保证（Python 版本、Node 版本、JDK 版本均未锁定）
- MySQL/Redis 等基础设施依赖需手动配置
- 无法快速横向扩展 YOLO Service 的推理实例

**优化方案**：引入 Docker Compose
- 每个服务提供 Dockerfile
- docker-compose.yml 编排全部服务 + MySQL + Redis
- 环境变量统一管理

**预期效果**：
| 指标 | 当前 | 优化后 |
|------|------|--------|
| 新环境部署时间 | 2-4 小时 | 15-30 分钟 |
| 环境一致性 | 手动保证 | Docker 保证 |
| YOLO 横向扩展 | 手动配置 | docker-compose scale |

## 2. 性能层面问题

### P2-01: 流媒体代理在 Java 进程内转码

**现状**：Backend 进程内通过 FFmpeg/Javacv 进行 RTSP→MJPEG 转码，每个摄像头消耗一个 FFmpeg 进程或一个 Javacv 线程。

**影响**：
- Java 进程承担转码计算负担，CPU 资源与业务逻辑竞争
- 单节点摄像头并发数受限于 Java 进程资源
- FFmpeg 进程泄露风险（异常时可能僵尸进程）

**量化影响**：
- 每路 MJPEG 转码约消耗 1-2% CPU（720p）
- 假设 16 路摄像头 → 16-32% CPU 仅用于转码
- 无流媒体连接池管理，并发观看者线性增长带宽

**优化方案**：引入独立流媒体服务器（MediaMTX / SRS）
- RTSP 流由流媒体服务器分发，支持 RTMP/WebRTC/HLS 多协议
- Backend 仅负责认证和 URL 签发
- 前端直接从流媒体服务器拉流

**预期效果**：
| 指标 | 当前 | 优化后 |
|------|------|--------|
| Backend 每路转码 CPU | 1-2%/路 | 0%（卸载到流媒体服务器） |
| 并发观看者上限 | ~20（带宽瓶颈） | ~500+（CDN/流媒体服务器） |
| 首帧延迟（MJPEG） | 1-3 秒 | <500ms（WebRTC） |
| 单节点摄像头容量 | ~16 路 | ~100+ 路 |

---

### P2-02: 统计查询无时序优化

**现状**：`stats_snapshot` 和 `env_sensor_sample` 表使用 MySQL 普通索引，无分区、无专用时序引擎。

**影响**：
- 随数据量增长（统计快照按小时写入，传感器数据高频采样），聚合查询越来越慢
- 7 天/30 天趋势查询需要全表扫描或索引范围扫描

**量化影响**：
- 假设 20 个场馆 × 50 个传感器 × 60 条/小时 = 60,000 行/小时
- 月累计 ~43,200,000 行传感器数据
- 当前无 EXPLAIN 验证查询计划效率

**优化方案**：引入 TimescaleDB 或 ClickHouse 处理时序数据
- 传感器采样和统计快照分区存储
- 自动压缩和过期策略

**预期效果**：
| 指标 | 当前（估算） | 优化后 |
|------|-------------|--------|
| 30 天聚合查询 | ~2-5 秒 | <200ms |
| 月数据量 | ~4300 万行 → 压缩比 1:1 | ~4300 万行 → 压缩比 10:1 |
| 存储成本 | 线性增长 | 自动过期+压缩 |

---

### P2-03: 前端 API 代码自动生成占比高

**现状**：`src/api/typings.d.ts` 约 2484 行自动生成代码，占前端总代码行数约 10%。

**影响**：
- 自动生成文件使用双引号+分号，手写文件倾向单引号无分号，代码风格不一致
- 无法手动修改生成代码，后端接口变更需重新生成全部
- `@ts-ignore` 注释在生成文件中抑止类型检查

**量化影响**：
- 自动生成代码：2484 行（typings）+ ~25 个控制器文件
- 手写代码与生成代码风格比：约 1:0.1（行数）
- 类型检查盲区：生成文件中 `/* eslint-disable */` + `@ts-ignore`

**优化方案**：
- 统一双引号+分号风格（与生成代码一致）
- 或为生成代码单独配置 `.eslintrc` 规则并排除自动生成目录

**预期效果**：
| 指标 | 当前 | 优化后 |
|------|------|--------|
| 全项目风格一致性 | ~60%（两种风格混用） | 100%（统一风格） |
| 类型检查覆盖率 | 生成文件跳过 | 全量覆盖 |
| 新人理解成本 | 需区分生成/手写 | 一目了然 |

## 3. 工程层面问题

### P3-01: 无 CI/CD 流水线

**现状**：四个子项目无自动化构建、测试、部署流程。

**影响**：
- 手动构建和部署，易出错
- 测试覆盖率无法自动统计
- 代码合并无质量门控

**量化影响**：
- 当前测试文件数：Backend 24 / Frontend 16 / YOLO 16 / Android 11
- 无自动测试执行记录
- 无自动化代码质量指标（如 lint 违规数）

**优化方案**：引入 GitHub Actions / GitLab CI
- 每次推送自动运行对应子项目的测试和构建
- 合并到 main 分支需通过全部检查

**预期效果**：
| 指标 | 当前 | 优化后 |
|------|------|--------|
| 构建验证 | 手动 | 自动门控 |
| 测试执行频率 | 开发者手动 | 每次推送 |
| 回归问题发现 | 发布后 | 合并前 |

---

### P3-02: 代码风格未强制统一

**现状**：四个子项目均无 Lint/Prettier/Format 工具配置。

- Backend：无 checkstyle、PMD、Spotless
- Frontend：无 ESLint、Prettier
- YOLO Service：有 ruff 依赖但无 .ruff.toml 配置
- Android：无 detekt、ktlint

**影响**：
- 代码审查耗费时间在格式讨论上
- 不同开发者提交风格不同
- 混用引号、缩进、分号风格

**量化影响**：
| 子项目 | 风格问题（估算） | 工具配置 |
|--------|-----------------|----------|
| Frontend | 引号风格混用率 ~30%（自动生成 vs 手写） | 无 |
| Backend | Entity snake_case 命名违反 Java 惯例 | 无 |
| YOLO | 导入排序无强制 | ruff（无配置） |
| Android | 函数参数格式不统一 | 无 |

**优化方案**：
| 子项目 | 推荐工具 | 配置 |
|--------|---------|------|
| Backend | Spotless + checkstyle | Google Java Format |
| Frontend | ESLint + Prettier | 统一双引号+分号 |
| YOLO | ruff | .ruff.toml：line-length=120, isort |
| Android | ktlint | ktlint gradle plugin |

**预期效果**：
| 指标 | 当前 | 优化后 |
|------|------|--------|
| 代码格式一致性 | 依赖人工审查 | 自动强制 |
| PR 审查时间 | 格式讨论占比高 | 格式自动处理 |
| 新人上手成本 | 需学习不成文约定 | 工具自动纠正 |

---

### P3-03: Android 无 ViewModel 和依赖注入

**现状**：Android 端直接在 Composable 中调用 `object` 单例仓库，无 ViewModel、无 DI 框架。

**影响**：
- 配置变更（旋转屏幕）导致状态丢失，需重新请求
- 单元测试困难（无法 mock 仓库依赖）
- Composable 逻辑与副作用耦合紧密

**量化影响**：
- 6 个页面全部使用 `produceState` 管理状态
- 0 个 ViewModel 文件
- 0 个 DI 模块
- 旋转屏幕后数据重新加载的页面比例：100%

**优化方案**：
- 引入 Hilt DI + ViewModel
- 状态提升到 ViewModel，Composable 仅负责渲染
- 仓库接口化，支持测试替身

**预期效果**：
| 指标 | 当前 | 优化后 |
|------|------|--------|
| 旋转屏幕状态保持 | 0%（全部重载） | 100%（ViewModel 保留） |
| 可单元测试的 UI 逻辑比例 | ~20% | ≥80% |
| 依赖可替换性 | 0%（硬编码单例） | 100%（DI 注入） |

---

### P3-04: 无统一日志聚合和监控

**现状**：四个服务各自输出日志到 stdout/文件，无集中式日志收集。

**影响**：
- 跨服务调试需要手动在多个终端查看日志
- 无结构化日志，难以搜索和过滤
- 无性能指标采集（响应时间、错误率、QPS）

**量化影响**：
- 日志聚合查询能力：0
- 性能指标监控能力：0
- 跨服务请求追踪：0（仅 Backend 有 requestId）

**优化方案**：引入 ELK Stack 或 Loki + Grafana + Prometheus
- 统一日志格式（JSON 结构化）
- 服务间请求追踪（traceId 传播）
- 关键指标仪表盘

**预期效果**：
| 指标 | 当前 | 优化后 |
|------|------|--------|
| 跨服务故障定位时间 | 30-60 分钟 | <5 分钟 |
| 性能异常发现时间 | 用户反馈驱动 | 仪表盘实时 |
| 日志搜索能力 | grep 多文件 | 全文索引查询 |

## 4. 安全层面问题

### P4-01: Android APP 使用 HTTP 明文通信

**现状**：`ApiClient.DEFAULT_BASE_URL` 使用 `http://192.168.0.181:8300`（HTTP 明文）。

**影响**：
- 所有 API 请求（含 JWT Token、用户密码）可被中间人窃取
- 不符合 Android 9+ 默认禁止明文流量的安全策略
- 生产环境无法通过安全审计

**优化方案**：
- 生产环境强制 HTTPS
- Android Network Security Config 限制明文仅开发环境

**预期效果**：
| 指标 | 当前 | 优化后 |
|------|------|--------|
| 通信加密 | 0%（明文 HTTP） | 100%（TLS 1.2+） |
| Token 窃取风险 | 高（局域网可达即可） | 低（需破 TLS） |

---

### P4-02: Android 认证存储使用 SharedPreferences

**现状**：`AuthSession` 使用 `SharedPreferences` 存储 JWT Token 和用户信息，且用户信息通过正则字符串拼接解析。

**影响**：
- Root 设备可读取 SharedPreferences XML
- 无加密存储
- 正则解析用户信息脆弱且不安全

**优化方案**：
- 使用 `EncryptedSharedPreferences` 或 Jetpack Security
- 使用 Gson 反序列化用户信息

**预期效果**：
| 指标 | 当前 | 优化后 |
|------|------|--------|
| Token 存储加密 | 无 | AES256 |
| 用户信息序列化 | 正则字符串拼接 | Gson JSON |
