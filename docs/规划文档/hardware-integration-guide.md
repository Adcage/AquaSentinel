# 硬件对接后续开发指南

> 本文档为硬件部分完成后的后端开发方向指引，仅描述功能模块、类和模式，不锁定具体字段名或实现细节。实际开发时需根据硬件能力与协议调整。

---

## 1. 背景

当前 AquaSentinel 的摄像头数据来源是外部 RTSP 流地址（手动配置），AI 推理也基于此。后续硬件部分（ESP32-CAM + 云台舵机等）开发完成后，后端需要：

1. 管理物理设备（注册、状态、鉴权）
2. 接入视频流（MJPEG HTTP 或 WebSocket 两种可能）
3. 发送控制指令（云台转动、预置位等）
4. 感知设备状态（在线离线、信号质量等）

硬件协议未定（MJPEG 流 / WebSocket 均有可能），因此本指南侧重**模块职责**和**扩展点**，而非具体属性定义。

---

## 2. 总体思路

```
ESP32-CAM 等硬件设备
    │
    ├── 视频流 ──────▶ YOLO Service（拉流 + 推理）
    │                  支持多种流源适配器
    │
    ├── 控制指令 ◀─── Backend（下发 PTZ / 预置位指令）
    │                  通过统一控制适配器
    │
    └── 心跳/状态 ──▶ Backend（设备注册与状态管理）
                       通过设备心跳机制
```

核心原则：**Backend 不知道也不关心硬件是什么，只通过适配器与抽象接口交互。**

---

## 3. Backend（Java）需要添加的功能模块

### 3.1 设备管理模块

当前 `CameraDevice` 实体只有静态信息（名称、流地址、状态等）。需要扩展为完整的设备生命周期管理：

- **设备注册与发现**：设备上线后自动或手动注册到系统，分配唯一标识与鉴权令牌
- **设备状态管理**：在线/离线/异常状态，基于心跳或流连接判定
- **设备配置下发**：向设备推送参数（分辨率、帧率、灵敏度等）
- **设备分组与关联**：设备归属场馆/区域，与当前场地模型对齐

涉及的新增类：
- 设备管理 Service（增删改查 + 状态切换）
- 设备心跳处理器（定时检测在线状态）
- 设备鉴权 Token 生成与校验

### 3.2 设备控制模块

这是云台控制的核心新增模块，当前代码中完全没有：

- **统一控制接口**：定义 PTZ（水平/垂直转动）、预置位、巡航等控制语义
- **控制适配器体系**：不同硬件协议对应不同适配器实现
  - ESP32-CAM 适配器：HTTP 接口控制舵机
  - ONVIF 适配器：标准摄像头云台协议（后续可能需要）
  - 其他自定义协议适配器
- **指令可靠性保障**：控制指令需要超时重试、幂等去重、结果回执
- **指令队列**：避免并发冲突，指令排队执行
- **控制限流**：防止短时间内发送过多指令导致硬件异常

涉及的新增类：
- 控制指令服务（接收指令、排队、下发、回执）
- 控制适配器接口（统一抽象）
- 各硬件型号的适配器实现类
- 指令超时与重试处理器

### 3.3 流地址解析模块

当前 `StreamProviderRouter` 只处理已知 RTSP 地址转 MJPEG。需要扩展为流地址动态解析：

- **流协议识别**：根据设备类型自动判断流协议（RTSP / MJPEG HTTP / WebSocket）
- **流地址模板化**：设备上线后根据设备信息动态拼接流地址，而非手动配置固定 URL
- **流健康检测**：定期探测流是否可用，标记异常设备

涉及的新增/改造类：
- 流地址解析器（根据设备信息生成流地址）
- 流健康检查器（定时探测流可用性）
- 对现有 `StreamProviderRouter` 的协议扩展

### 3.4 设备鉴权模块

当前流地址是裸 URL，无鉴权。硬件接入后需要：

- **设备身份认证**：设备连接时校验身份
- **控制指令签名**：防止恶意指令注入
- **流访问令牌**：限时令牌，防止 URL 泄露后被永久访问

涉及的新增类：
- 设备 Token 服务（签发、刷新、吊销）
- 签名验证拦截器（校验控制请求来源）

## 4. YOLO Service（Python）需要添加的功能模块

### 4.1 多流源适配模块

当前 `engine_task_service` 仅支持 RTSP 拉流（通过 OpenCV `VideoCapture`）。需要扩展为多协议源：

- **MJPEG HTTP 流适配器**：ESP32-CAM 最常见的输出方式
- **WebSocket 帧流适配器**：如果硬件选择 WebSocket 推送帧数据
- **RTSP 适配器**：保留当前能力
- **本地文件/测试流适配器**：开发调试用

适配器接口应统一：输出帧（numpy 数组）+ 帧时间戳 + 帧序号。

涉及的新增类：
- 流源适配器基类（定义统一的读帧接口）
- 各协议适配器实现
- 断流重连管理器（统一的重连与退避策略）
- 帧质量监控器（丢帧率、延迟统计）

### 4.2 流健康与重连模块

当前推理任务中的读帧线程缺乏健壮的重连机制：

- **连接状态机**：连接中 → 已连接 → 断开 → 重连中 → 已连接/失败
- **指数退避重连**：断开后按递增间隔重试，避免风暴
- **心跳检测**：长时间无帧判定为断流
- **帧超时丢弃**：积压帧超过阈值时丢弃旧帧，保证实时性

涉及的新增类：
- 流连接状态机
- 重连策略管理器
- 帧缓冲与丢弃策略

### 4.3 FPS 与资源调度模块

硬件场景下摄像头数量可能增加，需要按优先级分配推理资源：

- **动态 FPS 调整**：高风险区域高频推理（10-15fps），低风险区域低频（2-5fps）
- **任务优先级**：设备报警中提高帧率，空闲时降低
- **资源保护**：GPU 显存 / CPU 使用率超阈值时自动降低全局帧率

涉及的新增类：
- 推理调度器（按优先级分配帧率）
- 资源监控器（GPU/CPU 使用率）
- 动态 FPS 调整策略

## 5. 两端协同的接口约定

### 5.1 Backend ↔ YOLO Service

当前通过 WebSocket `/ws/ai-push` 通信。硬件接入后需要扩展消息类型：

- **新增控制指令转发**：Backend 下发 PTZ 控制指令 → YOLO Service 转发（或 Backend 直接下发到设备，YOLO Service 不参与控制）
- **新增设备状态同步**：YOLO Service 报告流连接状态（连接/断开/重连中）→ Backend 更新设备在线状态
- **新增推理调度指令**：Backend 指定某路流的推理优先级和 FPS → YOLO Service 动态调整

> 具体走哪种架构需要根据硬件能力决定：如果 ESP32-CAM 同时被 Backend（控制）和 YOLO Service（拉流）访问，需要注意并发冲突。

### 5.2 Backend ↔ 硬件设备

两种可能的架构：

**方案 A：Backend 作为控制中枢**
```
硬件 ──(视频流)──▶ YOLO Service（拉流）
硬件 ──(心跳)──▶ Backend（状态上报）
硬件 ◀──(PTZ指令)── Backend（控制下发）
```
优点：架构清晰，YOLO Service 只管推理  
缺点：Backend 需要维护设备连接

**方案 B：YOLO Service 作为设备代理**
```
硬件 ──(视频流)──▶ YOLO Service（拉流 + 转发控制）
YOLO Service ──(状态/报警)──▶ Backend
YOLO Service ◀──(PTZ指令)── Backend
```
优点：设备只需连接一个服务  
缺点：YOLO Service 职责过重

> 建议：先走方案 A（职责分离），如果 ESP32-CAM 同时只被一个服务访问的性能有问题，再考虑 B。

### 5.3 数据库模型扩展方向

当前 `camera_device` 表主要存静态信息。硬件接入后需要增加的字段方向：

- 设备连接协议类型
- 控制端点地址与令牌
- 设备硬件型号（用于选择适配器）
- 最后心跳时间
- 流协议类型与参数

> 不锁定具体列名，实际开发时根据硬件协议确定。

## 6. 开发优先级建议

硬件完成后，按以下顺序开发：

| 阶段 | 内容 | 预估 | 前置条件 |
|------|------|------|----------|
| 1 | 设备管理模块（注册、状态、鉴权） | 3-5 天 | 无 |
| 2 | 流源适配器（MJPEG/RTSP） | 3-5 天 | ESP32-CAM 流可用 |
| 3 | 设备控制适配器 | 3-5 天 | ESP32-CAM 控制接口可用 |
| 4 | 流健康检测与重连 | 2-3 天 | 阶段 2 完成后 |
| 5 | 推理调度与动态 FPS | 3-5 天 | 阶段 2 完成后 |
| 6 | 指令可靠性（重试、幂等、限流） | 2-3 天 | 阶段 3 完成后 |

## 7. 当前改造的约束原则

在硬件未完成之前，对 Java 和 Python 的日常改造需遵守以下原则，避免后续返工：

1. **不硬编码流协议**：所有涉及流地址的地方，保留 `protocol` 字段的扩展性，不要假设只有 RTSP
2. **不硬编码设备型号**：涉及设备属性的地方，通过适配器模式而非 if-else 判断型号
3. **保持 YOLO Service 的拉流模式**：当前是 YOLO 主动拉流（pull），即使硬件改为推流（push），也应保留拉流能力作为兜底
4. **设备控制走 Backend**：不把硬件控制逻辑混入 YOLO Service，保持推理服务职责单一
5. **消息格式保留扩展性**：现有 WebSocket 消息保留 `type` 字段或消息头，方便后续新增设备状态类消息
