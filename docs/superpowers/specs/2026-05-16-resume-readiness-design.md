# AquaSentinel 简历展示化补强设计

## 目标

将 AquaSentinel 从“子项目能力强、文档分散、运行入口不统一”的状态，补强为适合放入简历与作品集的完整项目形态。补强后的仓库需要同时满足三类读者：

1. 面试官：3 分钟内看懂项目价值、技术难点和个人贡献点。
2. 工程师：可以按文档启动核心链路并验证主要能力。
3. 自己：能用稳定、可复现的指标描述系统规模、质量和效果，而不是只讲功能。

本次工作不追求一次性把所有硬件链路完全容器化，而是优先建立“展示入口 + 核心运行闭环 + 指标证据”三件套。

## 现状判断

当前仓库已经具备较强的技术深度：

- 四端/多服务架构：Backend、Frontend、YOLO Service、Android。
- 实时视频链路：HTTP MJPEG、RTSP、HTTP-FLV、WebRTC、video-hub。
- AI 推理链路：YOLO + 跟踪 + 溺水判定 + WebSocket/回调联动。
- 工程化能力：独立 video-hub 微服务、Redis 同步、测试体系、架构文档、阶段总结文档。

但当前不利于简历展示的问题也很明确：

- 根目录缺少统一 README，信息分散在 `docs/` 和子项目 README。
- 缺少一键运行或最小运行入口，读者难以快速复现核心链路。
- 指标文档存在，但很多关键指标仍是 `[需测量]`，没有形成“可直接引用”的摘要。
- 文档偏开发过程记录，缺少面向作品集读者的结果导向表达。

## 方案概览

### 阶段一：展示层补强

新增根目录 `README.md`，作为项目的第一入口。该 README 不替代现有子项目 README，而是承担“总览与导航”角色。

README 需要覆盖这些内容：

- 项目一句话定位：水上安全监控系统，面向泳池/场馆的实时溺水检测与告警。
- 你做了什么：突出多协议视频、AI 推理、微服务拆分、实时告警、端到端验证。
- 核心亮点：用 5 到 8 条高价值要点表达系统难度，而不是平铺功能列表。
- 系统架构：链接已有架构文档，并在 README 放一个简化版文字架构图。
- 技术栈：按 Backend / Frontend / YOLO / Android / Infra 分组。
- 快速启动：只写最短路径，避免把所有历史环境细节堆到首页。
- 指标摘要：放经过验证的少量关键指标，并标明测试条件。
- 文档导航：把 `docs/项目现状`、架构文档、运行方案、指标文档串起来。

修改前，读者需要在多个目录里拼接理解项目；修改后，仓库首页本身就是一份压缩后的项目介绍页。

### 阶段二：运行层补强

补一个“核心链路可运行”方案，目标不是完整仿真全部硬件，而是让核心价值能落地验证。

推荐交付形式：

- 根目录新增运行文档，例如 `docs/运行部署/core-stack-quickstart.md`。
- 若当前条件允许，再补 `docker-compose.yml` 或等价脚本，覆盖核心依赖：MySQL、Redis、Backend、YOLO Service、video-hub-service，Frontend 视复杂度决定是否纳入。

运行方案的边界要明确：

- “核心链路可运行”包括：服务启动、接口健康检查、视频流通过 video-hub、YOLO 能消费视频帧、基础 API/状态可见。
- “依赖真实硬件/摄像头/模型文件/GPU 的增强能力”要单独说明，不把它们伪装成零门槛步骤。

这样做的价值是：

- 修改前，项目更像内部开发仓库；
- 修改后，它具备“别人能跑通核心演示”的作品属性。

### 阶段三：证据层补强

基于已有 `docs/项目现状/baseline-metrics.md`，整理出一版“简历可引用指标摘要”，并补齐当前最容易稳定复现的几项指标。

指标分为两类：

1. 已实测、可复现指标
- 代码规模
- 测试数量/通过情况
- Frontend 构建产物大小
- Backend / YOLO 启动耗时
- video-hub 与 YOLO 的 E2E 验证结果

2. 依赖真实运行环境的条件性指标
- GPU 推理延迟
- 实际 FPS
- 多路并发上限
- Android 端视频帧率/启动耗时

证据层的核心不是“把所有空白指标补满”，而是把当前最有说服力的 5 到 8 个指标做实，并写清采集方式与前提条件，避免指标失真。

## 交付物设计

本轮设计预期新增或修改以下文档与配置：

- 新增：`README.md`
  - 项目首页介绍、亮点、架构摘要、技术栈、快速启动、指标摘要、文档导航。
- 新增：`docs/运行部署/core-stack-quickstart.md`
  - 核心链路运行说明、依赖说明、启动顺序、验证步骤、已知限制。
- 视情况新增：`docker-compose.yml`
  - 如果现有服务启动边界清晰，补一个最小可运行栈；如果当前硬件/模型依赖过强，则先不强做 compose，而在文档中明确手动启动方案。
- 新增或补充：`docs/项目现状/resume-ready-metrics.md`
  - 面向简历与作品集的指标摘要，不替代详细 baseline 文档。
- 可能新增：`scripts/` 下的轻量验证脚本
  - 用于健康检查、服务可用性验证或指标采集。

## 取舍与边界

### 不做的内容

本轮不把以下内容作为硬目标：

- Android 完整打包与模拟器自动化演示
- 硬件摄像头、ESP32、STM32 全流程零配置复现
- 所有服务全部 Docker 化并覆盖所有开发场景
- 大规模补 UI 截图、宣传素材、演示视频剪辑

这些内容有价值，但会稀释当前最重要的目标：让仓库先具备“可理解、可运行、可量化”的最小展示闭环。

### 关键原则

- 只写真实可验证的内容，不包装不存在的能力。
- README 首页强调结果，不把开发过程文档原样搬上首页。
- 运行方案优先核心链路闭环，而非追求全量环境完美。
- 指标优先选择稳定、可重复、与你贡献直接相关的数据。

## 验证策略

交付完成后，需要验证三件事：

1. **展示验证**
- 新读者打开根 `README.md`，是否能在 3 分钟内理解项目价值、技术难点、系统边界和运行方式。

2. **运行验证**
- 按新文档能否启动核心服务。
- 至少能完成健康检查、基础服务联通验证，以及核心视频/推理链路中的一部分可观察结果。

3. **证据验证**
- README 中引用的每个指标，都能在对应文档中找到来源、方法或前提说明。
- 不出现“首页说得很满，正文没有证据支撑”的情况。

## 实施顺序

按你确认的顺序执行：

1. 先补 `README.md` 与文档导航。
2. 再补核心运行方案与必要配置。
3. 最后补指标摘要与验证说明。

这样做可以保证每一步都能独立产出价值：即使第二步或第三步需要迭代，第一步的展示层也已经能显著提升项目的简历可用性。
